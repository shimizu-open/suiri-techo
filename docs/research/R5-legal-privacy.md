## 1. 個人情報保護法

### 1-1 小さな個人サービスも対象か → 対象になる
- 法16条2項は「個人情報取扱事業者」を、**個人情報データベース等を事業の用に供している者**と定めている（国の機関などは除く）。件数の下限はない。
- PPC ガイドライン（通則編）2-5 は「事業」をこう説明する。「一定の目的をもって反復継続して遂行される同種の行為であって、かつ社会通念上事業と認められるもの…営利・非営利の別は問わない」。さらに「個人であっても…個人情報取扱事業者に該当する」。
- PPC Q&A 1-50 は件数の多い少ないを問わないとしている。Q&A 1-54 は、営利でも非営利でも当たりうる例として自治会やサークルを挙げている。
- このアプリは、他人（保護者・子ども・施術者など）の Google アカウント情報を繰り返し預かる。**対象になる前提で作る**。

### 1-2 公表が必要な事項（法32条1項、施行令10条）
「本人の知り得る状態」に置く。法32条1項の括弧書きにより、**本人から求められたときに遅滞なく答える形でもよい**。
1. 氏名と住所。住所は「請求があれば遅滞なく回答」とすれば、自宅住所をサイトに載せなくて済む（同項の括弧書きによる）。
2. すべての保有個人データの利用目的（法17条で「できる限り特定」が求められる。法21条では、取得の前に公表していなければ取得後に通知または公表する）。
3. 開示・訂正・利用停止などの請求に応じる手続（手数料を取るならその額も）。
4. 安全管理のために講じた措置（施行令10条1号。書くと安全管理に支障が出る事項は除く）。
5. 苦情の申出先（施行令10条2号）。
6. 認定個人情報保護団体に入っている場合はその団体。今回は該当しない。

開示請求には、電磁的記録（データ）で渡す方法で応じなければならない（法33条1項・2項）。アプリ内で自分のデータをダウンロードできれば、手続はほぼそれで足りる。

### 1-3 AWS と Google（外国の扱い）
- **AWS**：AWS Customer Agreement の契約当事者の表では、Account Country が Japan なら「Amazon Web Services Japan G.K.」、準拠法は日本法、裁判所は東京地裁になっている（https://aws.amazon.com/agreement/ ）。東京リージョンなら、**事業者も保存場所も日本**になる。
  - PPC Q&A 7-53 では、クラウド事業者が保存データを「取り扱わない」ことになっていれば（契約で定めがあり、アクセス制御もしている場合）、第三者への「提供」に当たらない。ただし Q&A 7-54 のとおり、安全管理措置は自分で講じる必要がある。
  - アカウントの国が日本以外の場合は Q&A 10-25 が当てはまる。外国にあるクラウド事業者を使うときは、**事業者の所在国とサーバーの所在国の両方**を公表する。サーバーが日本国内にあっても同じ扱いになる。運営者の AWS アカウントの国は**未確認**なので、請求先住所を確かめる。
- **CloudFront**：ログイン後の画面がエッジでキャッシュされると、別の人に表示される事故が起きうる。ログイン後の応答には `Cache-Control: private, no-store` を付ける。
- **Google**：Google LLC は米国の会社で、米国は法28条の「同等の水準にある外国」に入っていない。カレンダー連携は、本人が自分の操作で自分の Google カレンダーに書き込むものなので、「第三者提供」に当たるかどうかは解釈が分かれうる（PPC の明示的な見解は**未確認**）。安全側に倒し、連携ボタンの前に「送る項目」と「米国 Google LLC のサービスであること」を出して同意をもらう。
- **Google 自身のルール**（Google API Services User Data Policy, https://developers.google.com/terms/api-services-user-data-policy ）：
  - Google ユーザーデータの扱いを全部書いたプライバシーポリシーが必須。
  - 使ってよいのは、画面で目立つ利用者向け機能のためだけ（Limited Use）。
  - 広告に使う・売るのは禁止。
  - **人が中身を読むのは、本人の同意、セキュリティ、法令対応などの場合に限る**。
  - データは「通信中も保存中も安全に」守ることが求められる。
  - カレンダーのスコープは確認（verification）が必要になる場合がある（https://support.google.com/cloud/answer/13463073 ）。詳しい手順は Google 連携の調査に任せる。

### 1-4 漏えいしたとき（法26条、施行規則7条・8条）
次のどれかに当たると、PPC への報告と本人への通知が義務になる。
- 要配慮個人情報を含む漏えい：**件数を問わない**。ただし「高度な暗号化」などの措置をしていれば除かれる。
- 不正の目的による漏えい（不正アクセスなど）：**件数を問わない**。
- 1,000人を超える漏えい。

報告は、知った後に速やかに行い、確報は30日以内（不正アクセスの場合は60日以内）に出す（規則8条）。
→ サーバーが一度でも侵入されれば、数十人規模でも報告が必要になる。**要配慮情報を最初から持たない設計**にしておくと、この負担と危険が大きく減る。

## 2. 要配慮個人情報（施術者がお客さまの症状を書く場合）

### 2-1 何が該当するか
- 法2条3項は病歴を例に挙げる。施行令2条は、心身の機能の障害、**医師その他医療に関連する職務に従事する者（医師等）**による健康診断などの結果、医師等による指導・診療・調剤を受けたことを加えている。
- ガイドライン 2-3 の説明：
  - 病歴は「病気に罹患した経歴…（例：特定の個人ががんに罹患している、統合失調症を患っている等）」。
  - 身長・体重・血圧などは「健康診断、診療等の事業…とは関係ない方法により知り得た場合は該当しない」。
- このアプリに当てはめると、次のようになる。
  - 「病院でヘルニアと言われた」「うつで通院中」「薬を飲んでいる」→ **該当する**（病歴、診療・調剤）。
  - 「右肩が上がって見えた」「歩くとき左をかばう」など、施術者が見たこと → 病歴にも医師等による検査結果にも当たりにくい。ただし、鍼灸師・あん摩マッサージ指圧師・柔道整復師が「医療に関連する職務に従事する者」に含まれるかは**未確認**。含まれるなら、その人たちの検査結果に当たる記録は該当しうる。
- そもそも、**特定の個人を識別できなければ個人情報ではない**ので、要配慮個人情報にもならない（法2条1項）。ただし「他の情報と容易に照合」して識別できるものは個人情報になる。容易かどうかは「事業者の実態に即して…判断」される（ガイドライン 2-1）。

### 2-2 同意の要否
- 要配慮個人情報は、あらかじめ本人の同意を得ないと取得できない（法20条2項）。
- ただし、本人から書面や口頭で直接受け取った場合は「本人が当該情報を提供したことをもって…同意があったものと解される」（ガイドライン 3-3-2）。施術者が問診でお客さまから聞くこと自体は、通常は問題になりにくい。
- 問題になるのは、**それを運営者のサーバーに置くこと**である。運営者が中身を「取り扱う」と見られれば、施術者から運営者への提供になりうる。運営者が閲覧しないと規約で約束し、アクセスも制御していれば、Q&A 7-53 と同じ考え方で「提供に当たらない」と整理できる余地はある。ただし、運営者がデータベースを直接触れる立場にある以上、グレーが残る。

### 2-3 対策の選択肢と評価
| 案 | 効果 | 評価 |
|---|---|---|
| A. お客さま単位の記録（顧客ページ・顧客ID欄）を作らない | 運営者側でデータが「人ごと」に整理されない | **必須** |
| B. 名前・連絡先・生年月日・写真・病名・通院・服薬を書かないよう、入力欄に案内を出す | 誤入力を減らす | **必須** |
| C. イニシャルで書く | 施術者は予約表と照合できてしまう | **不十分**。勧めない |
| D. 番号で書き、対応表はアプリの外に置く | 運営者からは識別できない。施術者からは照合できる | 施術者の自己責任とし、アプリに番号欄は作らない |
| E. 運営者は中身を見ない（管理画面なし・規約で約束） | 「提供に当たらない」整理を支える。Google の方針とも合う | **必須** |
| F. 項目ごとに暗号化 | 鍵が同じサーバーにあると、侵入されたときには効かない | 補助。頼りにしない |

**実務上十分か**：A・B・E をそろえれば、運営者の手元には「誰かわからず、病名も含まない、施術者自身の考え方のメモ」しか残らない。施術者から見ると、汎用のメモアプリに自分の記号で書くのと同じ位置づけになる。数人〜数十人の閉じた無料サービスとしては合理的な線である。

ただし完全ではない。自由記述欄に書かれてしまうことは防ぎきれないし、施術者の側では照合できる。お客さまごとの経過を本格的に預かる施術者向けツールに進むなら、本人同意の取り方、暗号化、厚労省「医療情報システムの安全管理に関するガイドライン」（第7.0版、令和8年6月。https://www.mhlw.go.jp/stf/shingi/0000516275_00006.html ）を参照する別の設計が要る。このガイドラインは「医療機関等」向けで、施術所が含まれるかは**未確認**。

## 3. 医師法・あはき法・柔道整復師法・民間療法

- 医師法17条：「医師でなければ、医業をなしてはならない」。厚労省の通知（医政発第0726005号、平成17年7月26日。https://www.mhlw.go.jp/web/t_doc?dataId=00tb2895&dataType=1&pageNo=1 ）は、医業を「医師の医学的判断及び技術をもってするのでなければ人体に危害を及ぼし、又は危害を及ぼすおそれのある行為(医行為)を、反復継続する意思をもって行うこと」と説明している。医行為の定義を示した最高裁令和2年9月16日決定（タトゥー事件）は、裁判所サイトがメンテナンス中で本文は**未確認**。
- あはき法1条は、あん摩マッサージ指圧・はり・きゅうを業とするには免許が必要と定める。12条は、それ以外の医業類似行為を業とすることを禁じている（柔道整復は柔道整復師法による）。柔道整復師法15条は、医師と柔道整復師以外が柔道整復を業とすることを禁じている。
- 民間の整体・カイロには国の資格制度がない。あはき法12条の禁止範囲を限定して解した最高裁昭和35年1月27日判決と、厚生省の平成3年の通知（医事第58号）は、検索の上限に達したため**未確認**。

**アプリへの当てはめ**：アプリは体に触れず、施術もしない。危ないのは**アプリやその文言が「診断」や「治療の提案」をしているように見えること**と、施術者の業務範囲を超えた判断を促すことである。
- 避ける言葉：診断・診察・問診・治療・治す・処方・効く・改善させる・症状チェック・原因を特定・病名・「〇〇の可能性があります」（アプリや AI が言う形）・おすすめの施術。
- 使う言葉：観察・気づき・仮説（自分の考え）・確かめる・振り返り・記録・次に見ること。
- 「仮説」は**施術者自身の考え方の練習**として扱う。アプリが体について結論を出すことはしない。

## 4. 薬機法のプログラム医療機器

- 薬機法2条4項は医療機器を「疾病の診断、治療若しくは予防に使用されること、又は…身体の構造若しくは機能に影響を及ぼすことが目的とされている機械器具等」と定めている。
- 厚労省「プログラムの医療機器該当性に関するガイドライン」（令和3年3月31日、令和5年3月31日一部改正。https://www.pmda.go.jp/files/000240233.pdf ）の要点：
  - 医療機器に当たるかは「製品の**表示、説明資料、広告等**に基づき、当該プログラムの**使用目的及びリスクの程度**」で判断する。同じ機能でも、使用目的が違えば判断が変わりうる。
  - 機能が複数ある場合、1つでも医療機器の定義を満たせば全体が規制される。
  - 医療機器に当たらない典型例：患者説明用、院内業務の支援、使用者が自分の健康記録を見るもの、スポーツなど医療・健康以外を目的とするもの、生命や健康への影響がほとんどないもの。
  - 個人を特定して具体的な病名や罹患の可能性を表示するものは、「使用者によらず、診断に用いられるもの」として判断する。
  - 医療機器でないものには、「疾病の診断、治療又は予防に使用されることを目的としていない」または「医療機器ではない」と書くことが望ましい。ただし脚注12のとおり、そう書いても「疾病の疑いを判断できるなど」と宣伝すれば医療機器に当たる。
- 事例集（事務連絡、令和5年3月31日。https://www.pmda.go.jp/files/000251980.pdf ）は、医療関係者が使うもののうち「医学的判断に使用しない情報提供のみを目的とした」ものとして、医学教育用のトレーニング教材などを医療機器に当たらない例に挙げている。

**当たらないための条件**（このアプリの決まり）
1. 目的は「観察・仮説・検証・振り返りという考え方の練習と記録」に限り、画面にも宣伝にもそう書く。
2. 病名、病気のリスク、体の状態の判定を表示しない。病名の辞書も持たない。
3. 入力された体の情報をもとに、個人向けの助言や施術の提案を出さない（AI を使う場合も同じ）。
4. 「施術の効果が上がる」「見落としを防ぐ」など、医療の判断を支えるような宣伝をしない。

## 5. 効果の宣伝（景品表示法の不実証広告規制）

- 景表法5条1号は、商品・役務の内容を実際より著しく優良に見せる表示を禁じている。7条2項により、消費者庁は根拠資料の提出を求めることができ、出せなければ違反とみなされる。
- 運用指針（平成15年公正取引委員会、平成28年消費者庁一部改正。https://www.caa.go.jp/policies/policy/representation/fair_labeling/guideline/pdf/100121premiums_34.pdf ）によると、根拠と認められるには①客観的に実証された内容であること（試験・調査、または専門家の見解・学術文献）、②表示した効果と実証された内容が適切に対応していることの両方が必要。利用者の体験談は、無作為抽出などで統計的な客観性が十分になければ根拠として認められない。
- 景表法の対象は「自己の供給する商品又は役務の取引」についての表示（5条）。無料で取引がない今の形は対象外の可能性が高いが、確定はさせていない（**未確認**）。将来、施術者向けに有料で提供するなら対象になる。運営者の「誇張しない」方針もあるので、**今から対象になる前提で書く**。
- 使わない：頭が良くなる、論理的思考力が伸びる、IQ が上がる、脳が活性化する、認知症予防、〇日で身につく、科学的に証明された。健康にかかわる効果をうたうと、4章の医療機器の論点にも触れる。
- 使ってよい：「観察・仮説・検証・振り返りを毎日くり返すための道具」「自分の考えの記録が残る」。研究を引用するなら、何が示されたのかを正確に書く（効果の強さは他の調査に任せる）。

## 6. 子どもの利用

- 個人情報保護法には年齢の一律の定めがない。PPC Q&A 1-62 は「一般的には12歳から15歳までの年齢以下の子どもについて、法定代理人等から同意を得る必要がある」としている（同意が必要な場面での話）。
- 民法4条で成年は18歳。民法5条では、未成年者が法定代理人の同意なしにした法律行為（利用規約への同意も含む）は取り消すことができる。
- Google アカウント：日本は例外国の一覧に入っていないため、**13歳**が自分でアカウントを管理できる最低年齢になる。それより下はファミリーリンクで保護者が管理する（https://support.google.com/accounts/answer/1350409?hl=ja ）。保護者が管理するアカウントで外部アプリに Google ログインできるかは**未確認**。
- 実務：子どもは保護者の同意のもとで使う。登録時に「18歳未満は保護者の同意を得た」ことを確認する。生年月日や学校名は取らない。

## 7. 利用規約の最小限

- 定型約款：あらかじめ「規約を契約の内容とする」と表示し、同意を得れば、個々の条項にも合意したとみなされる（民法548条の2）。ただし、相手の利益を一方的に害する条項は合意しなかったものとみなされる（同条2項）。
- 規約の変更：変更する旨、変更後の内容、効力が生じる日をインターネットなどで周知すれば、個別の同意なしに変更できる（民法548条の4）。
- 免責：消費者契約法が適用される前提で書く。個人の無料運営が同法の「事業者」（2条2項：事業として契約の当事者となる個人）に当たるかは確定できないが、安全側に倒す。
  - **責任を全部免除する条項は、過失の程度にかかわらず無効**（8条1項1号・3号）。
  - 故意・重過失による責任の一部免除も無効（同項2号・4号）。
  - 軽過失に限った一部免除は、**「重大な過失を除く過失にのみ適用」と明記しないと無効**（8条3項）。
  - そのため「一切責任を負いません」とは書かない。

## 8. 安全管理（個人の運営で現実的にできること）

- 法23条は安全管理措置を義務づけている。ガイドライン10（別添）は、基本方針・取扱規律・組織的・人的・物理的・技術的・外的環境の把握の7区分で手法の例を示している。
- 「中小規模事業者」は従業員100人以下が目安。ただし、過去6か月以内のどこかで個人データの本人数が5,000を超えたことがある者などは除かれる。このアプリは該当し、簡単な手法の例でよい。
- ガイドラインが中小規模事業者向けに挙げる技術面の例：
  - 取り扱う機器と人を明確にする。
  - ユーザー制御機能で識別・認証する。
  - OS とセキュリティソフトを最新に保つ。
  - ファイルを送るときはパスワードを付ける。
- 上の7区分をこのアプリに当てはめると、次のようになる。

| 区分 | このアプリでやること |
|---|---|
| 基本方針・規律 | プライバシーポリシーに方針を書く。取得・保存・削除の手順をリポジトリに短く残す |
| 組織的 | 責任者は運営者1人。漏えいに気づいたときの手順（止める→範囲を調べる→PPC報告→本人へ連絡）を決めておく |
| 人的 | データベースに触れるのは運営者のみ。協力者を入れるなら守秘を約束してもらう |
| 物理的 | 開発PCのディスク暗号化と画面ロック。本番データを手元PCに置かない |
| 技術的 | 全通信を HTTPS にする（CloudFront からオリジンまで）。Google ログインのみ。**自分のデータしか見えない認可**。DB は外部に公開しない。管理アクセスは鍵か SSM。OS とパッケージを更新する。EBS とバックアップを暗号化する。ログに入力本文を出さない |
| 外的環境 | 日本の AWS アカウントと東京リージョンにする（違う場合は国名を公表する） |

- 安全管理措置は公表事項（施行令10条1号）なので、上の表をそのままポリシーに箇条で書けばよい。
- 法22条は、不要になったデータを遅滞なく消去する努力義務を定めている。退会したら即時に削除し、バックアップは決まった日数で消えることを書く。

## 9. アプリへの示唆

### 9-1 やってはいけないことリスト
1. お客さま（他人）単位の記録画面・顧客ID欄・カルテ機能を作らない。
2. 病名、病気のリスク、体の状態の判定を、アプリや AI が表示しない。病名辞書や症状チェック機能も持たない。
3. 「診断・治療・効く・改善・処方・おすすめの施術」という言葉を UI と宣伝で使わない。
4. 「頭が良くなる」「思考力が伸びる」「脳トレ」「認知症予防」など、効果を約束する表現を使わない。
5. 運営者が利用者の記録を閲覧できる管理画面を作らない。障害対応・本人の依頼・法令の場合を除き、中身を読まない。
6. 観察メモの本文を Google カレンダーや外部 AI に送らない。カレンダーへ送るのはタスクの題名と日時だけにする。
7. アクセス解析タグ・広告タグを入れない。入れると、電気通信事業法の外部送信規律（総務省ページ https://www.soumu.go.jp/main_sosiki/joho_tsusin/d_syohi/gaibusoushin_kiritsu.html 。このアプリに適用されるかは**未確認**）と Google の方針の確認が増える。
8. 施術の事例や効果を公開・共有する機能を作らない。
9. ログイン後の画面を CloudFront でキャッシュしない。
10. 生年月日・学校名・住所・電話番号を取らない。

### 9-2 画面に出す注意書きの文案
- **すべての入力欄の下（小さく常時）**
  「ここに書くのは、あなた自身の観察と考えです。ほかの人の名前・連絡先・顔写真、病名や通院のことなど、その人がわかる情報や健康の情報は書かないでください。人のことは『同僚A』『電車の向かいの人』のように書いてください。」
- **施術の振り返りを書く画面（初回はダイアログ、以降は入力欄の上）**
  「この画面は、施術者ご自身の『見方・考え方』を振り返るためのものです。お客さまの記録（カルテ）には使えません。お客さまの名前・イニシャル・会員番号・生年月日・写真・病名・通院や服薬のことは書かないでください。書くのは、あなたが見たこと（例：右肩が上がって見えた）と、あなたの仮説と、次に確かめたいことだけです。」
- **フッターとアプリの説明ページ**
  「このアプリは、日常の観察と考え方を練習するための道具です。医療機器ではなく、病気の診断・治療・予防を目的としていません。体の不調は医師にご相談ください。」
- **効果について（説明ページ）**
  「使えば考える力が伸びる、とはお約束しません。観察・仮説・検証・振り返りを毎日くり返し、その記録を残すための道具です。」
- **Google カレンダー連携ボタンの前**
  「連携すると、タスクの『題名と日時』を、あなたの Google カレンダーに書き込みます。Google カレンダーは米国の Google LLC のサービスです。観察メモの本文は送りません。連携は設定画面からいつでも解除できます。」［同意して連携する］
- **初回登録**
  「13歳以上の方がご利用いただけます。18歳未満の方は、保護者の方の同意を得てからご利用ください。」 □ 利用規約とプライバシーポリシーに同意します（18歳未満の方は保護者の同意を得ています）

### 9-3 プライバシーポリシーの骨子
1. 運営者：氏名とメールアドレス。住所は「ご請求があれば遅滞なくお知らせします」（法32条1項）。
2. 取得する情報：
   - Google アカウントの名前・メール・アイコン・ID
   - カレンダー連携のトークン
   - 利用者が入力した内容
   - アクセスログ（IP アドレス・日時・ブラウザ）
3. 利用目的：アプリの提供とログイン、カレンダー連携、問い合わせへの対応、不正利用の防止と障害対応。広告・販売・AI の学習には使わない。
4. 第三者提供：しない（法令に基づく場合を除く）。
5. 外部サービス：
   - Google（米国。ログインとカレンダー）
   - AWS（日本法人、東京リージョン）
6. 運営者による閲覧：原則として見ない。例外は本人の依頼、障害対応、法令に基づく場合だけ。
7. Google ユーザーデータ：Google API Services User Data Policy（Limited Use を含む）に従う。
8. 安全管理措置：8章の表を箇条で書く。
9. 保存期間と削除：退会したら即時に削除する。バックアップからは最長◯日で消える。連携トークンは Google 側でも失効させる。
10. 開示・訂正・利用停止・削除：アプリ内のダウンロード機能と削除機能で行える。ほかに、登録したメールアドレスから連絡を受け付ける（本人確認を兼ねる）。手数料は無料。
11. 子ども：13歳以上。18歳未満は保護者の同意を得る。
12. Cookie：ログインを維持するためだけに使う。解析・広告には使わない。
13. 問い合わせ・苦情の窓口：メールアドレス。
14. 改定：アプリ内で告知し、施行日を明記する。制定日も書く。

### 9-4 利用規約の骨子
1. 適用と同意（定型約款）。
2. サービスの目的：考え方の練習と記録の道具。医療・診断・治療ではない。効果は保証しない。
3. 利用資格：13歳以上。18歳未満は保護者の同意を得る。招待制。
4. アカウント：Google アカウントの管理は本人が責任を持つ。
5. 禁止事項：
   - 法令違反
   - 他人を特定できる情報や健康・病歴の情報を入力すること
   - 顧客記録・カルテとして使うこと
   - 不正アクセスやサーバーに負荷をかける行為
   - なりすまし
6. 施術者の責任：お客さまの情報は、施術者自身が法令に従って管理する。アプリには書かない。
7. 入力データ：利用者のものとする。運営者はサービス提供のためだけに扱う。
8. 変更・中断・終了：終了するときは30日前までに告知し、その間はデータをダウンロードできるようにする。終了後はすべて削除する。
9. 退会：いつでも退会できる。退会するとデータは削除される。
10. 免責（消費者契約法8条に沿わせる）：
    - ①特定の目的への適合、効果、不具合がないことは保証しない。
    - ②運営者の故意・重過失による損害は、法令に従い責任を負う。
    - ③運営者の過失（重大な過失を除く）による損害は、直接かつ通常の損害に限り責任を負う。
11. 規約の変更：効力が生じる日を決め、アプリ内で周知する（民法548条の4）。
12. 準拠法と管轄：日本法。

### 9-5 データ設計の決まり
1. テーブルは「利用者」を軸にする。customer、patient、client のような**他人を表すテーブル・カラムを作らない**。
2. すべての取得系クエリを `user_id` で絞る（ポリシーで強制し、テストで確かめる）。管理者がメモ本文を読める画面は作らない。
3. カレンダーに送る項目はタスクの題名・日時・アプリ内リンクだけ。メモの本文は送らない。
4. OAuth のトークンは暗号化して保存する（Laravel の encrypted cast）。スコープは最小にする。退会と連携解除のときは Google の失効エンドポイントを呼ぶ。
5. 退会したら、その利用者の行をすべて物理削除する。バックアップの保持日数を決め（例：7日）、ポリシーと同じ数字にする。
6. 自分のデータをすべて JSON/CSV でダウンロードできるようにする（開示請求への対応を兼ねる）。
7. アプリのログとエラー通知に入力本文を出さない。リクエストボディは記録しない。
8. 入力に電話番号やメールアドレスの形があれば、保存前に「他人の情報ではありませんか」と警告する（止めはしない）。
9. 画像を扱うなら、位置情報（EXIF）を消す。他人の顔は載せない案内を出す。
10. ログイン後の応答には `Cache-Control: private, no-store` を付ける。全通信を HTTPS にする。EBS とスナップショットを暗号化する。
11. 招待制（メールアドレスの許可リスト）にする。年齢は「13歳以上・18歳未満は保護者同意」のチェックだけを持ち、生年月日は持たない。
12. 外部 AI に本文を送る機能は v1 では作らない。作るなら、外国にある第三者への提供（法28条）と Google の方針を整理してからにする。
