0地図の読み方：住所の表から画面まで

この解説を読む人として、どの章から読んでも迷わないように、まず「ブラウザとサーバーのやりとり」と、プログラムの入口である住所の表（routes/web.php と routes/web/{機能}.php）の読み方を知りたい。だから、最初に全体の地図を見る。

この章で追う道筋：アドレスバーに URL → ブラウザがお願い（リクエスト）を送る → web の箱（nginx）→ public/index.php → bootstrap/app.php → 見張り役（ミドルウェア）の3段 → routes/web.php が読み込んだ routes/web/{機能}.php で行き先を決める → 受付（コントローラー）→ 形の検証・権限・用事・読み出し → 表（データベース）→ 画面（Blade と部品）→ 返事（レスポンス）

お願いと返事、4つの箱

  1. ブラウザ

    すべては「お願い」と「返事」の1往復でできている

    画面を開く・ボタンを押す・フォームを送る。推理手帳の利用者のどの行動も、ブラウザからサーバーへの1回の リクエスト（お願い）と、サーバーからブラウザへの1回の レスポンス（返事）でできています。返事の中身は、画面の HTML か、「別の住所へ行ってください」という 転送（リダイレクト）のどちらかです（推理手帳には、画面の中のプログラムがデータだけをやりとりする所がほとんどありません。あとで説明します）。

    たとえると図書館の貸し出しカウンターです。利用者（ブラウザ）が申込用紙（リクエスト）を出し、カウンター（サーバー）が本（レスポンス）を渡します。「その本は2階のカウンターで」と案内されるのが転送です。案内されたら、利用者はもう一度そのカウンターに用紙を出し直します（ブラウザが自動でもう1回リクエストを送る）。
    お願いに書いてあること
    • メソッド：GET（見せて）・POST（これを受け取って・何かして）・PATCH／PUT（書き換えて）・DELETE（消して）。HTML のフォームは GET と POST しか送れないので、Laravel はフォームの中の隠し欄 _method で PATCH・PUT・DELETE を表します（Blade では @method('DELETE') と書く）。推理手帳では、直すのは PATCH（○× と週のふりかえりは PUT）、消す・取り消すのは DELETE です。
    • 住所（パス）：/today・/tasks・/cases/12 など。
    • Cookie：前にサーバーから渡された「番号札」。ブラウザはそのサイトに来るたびに自動で送ります（ログインの見分けに使う。1章）。
    • 中身：POST のときはフォームに入れた値（題名・本文など）と、ニセの送信を見分ける合言葉 _token。
    返事に書いてあること
    • 状態の番号：200（成功）、302（転送。行き先は Location に書く）、403（あなたには許されていない。他人の記録など）、404（その住所・その番号の記録はない）、419（ニセの送信の疑い）、429（回数が多すぎる）、500（サーバーの中の失敗）。403・419・429 のしくみは 11章。
    • Cookie を渡す：Set-Cookie。番号札を渡したり、書き換えたりします。
    • 守りの札：どの返事にも、セキュリティのヘッダが付きます（11章）。
  2. サーバー

    サーバーの中は4つの箱（Docker）

    Docker は、プログラムを「箱（コンテナ）」に入れて、どのパソコンでも同じように動かす道具です。推理手帳は4つの箱で動きます。箱の組み合わせは、プロジェクト直下の docker-compose.yml に書いてあります。

    docker-compose.yml
    services:
  # PHP（Laravel）を動かす係。画面の CSS・JS のビルド（Node.js）もここで行う
  app:
    build: ./infra/php
# …（省略）…
  # 決まった時刻の仕事（カレンダーの取り込み・期限の過ぎたキャッシュの掃除）と、後回しにした仕事（カレンダーへの書き込み）を片づける係
  worker:
    build: ./infra/php
    user: "1000:1000"
    command: sh -c "php artisan schedule:work & php artisan queue:work --sleep=3 --tries=3 --max-time=3600"
# …（省略）…
  # 入口（nginx）。ブラウザからの通信を受けて、PHP の係に渡す
  web:
    image: nginx:1.27-alpine
# …（省略）…
  # データベース（MySQL）
  db:
    build: ./infra/mysql
    4つの箱の役目
    • web（nginx）：入口の門番。CSS・JS・画像のような「置いてあるだけのファイル」は自分で返し、それ以外を app に回す。
    • app（PHP 8.4 と Laravel 13）：お願いを受けて、記録を読み書きし、画面を作る。この解説のほとんどは、この箱の中の話です。
    • db（MySQL 8.4）：記録の保管庫。利用者・事件・タスク・予想などの表と、セッション・キャッシュ・後回しの仕事（jobs）の表もここにあります。
    • worker：app と同じ中身で、画面を作らずに裏の仕事だけをする係。queue:work が後回しにした仕事（カレンダーへの書き出し）を片づけ、schedule:work が決まった時刻の仕事（15分ごとの取り込み・5分ごとのキャッシュの掃除・毎日の AI の通行証の掃除）を始めます（9章・13章）。
    たとえるとweb は店の入口の案内係、app は厨房、db は食材の倉庫、worker は閉店後や決まった時刻に仕込みをする裏方です。客（ブラウザ）と話すのは入口と厨房だけで、裏方は客を待たせずに働きます。
  3. サーバー

    web の箱（nginx）：ファイルならそのまま返し、ほかは Laravel へ

    infra/nginx/default.conf
        if ($http_content_type ~* "multipart/form-data") { return 415; }
// …（省略）…
    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }

    location ~ \.php$ {
        fastcgi_pass app:9000;
    • 1行目：ファイルを送る形（multipart/form-data）の送信は、PHP に届く前に「415（受け付けない形）」で止めます。推理手帳にはファイルを上げる機能がないので、使わない入口を閉じておくためです。
    • try_files は「その名前のファイルがあればそれを返す。なければ index.php に回す」という意味です。/build/assets/app-….css はファイルがあるので nginx がそのまま返し、/today のようなファイルのない住所は index.php に回ります。
    • .php の仕事は fastcgi_pass app:9000 で app の箱の 9000 番へ渡します。
  4. サーバー

    Laravel の入口：public/index.php と組み立て図 bootstrap/app.php

    Laravel に回ってきたお願いは、必ずこのファイルから始まります。お願いを Request（リクエストの中身をまとめた入れ物）にして、アプリに渡します。

    src/public/index.php
    // Bootstrap Laravel and handle the request...
/** @var Application $app */
$app = require_once __DIR__.'/../bootstrap/app.php';

$app->handleRequest(Request::capture());

    bootstrap/app.php は、アプリの組み立て図です。「住所の表はどこか」「見張り役に何を足すか」「ログインしていない人をどこへ送るか」をここで決めています。

    src/bootstrap/app.php
    return Application::configure(basePath: dirname(__DIR__))
    ->withRouting(
        web: __DIR__.'/../routes/web.php', // 中身は routes/web/{機能}.php。web.php はそれを読み込むだけ
        commands: __DIR__.'/../routes/console.php',
        health: '/up', // 死活確認の住所（アプリが動いているか）
    )
    ->withMiddleware(function (Middleware $middleware): void {
        $middleware->alias([
            'agreed' => EnsureAgreed::class, // ルートで middleware('agreed') と書くと、同意前の人を /agree へ送る
        ]);
        // どの画面にも守りの札（セキュリティのヘッダ）を付ける。ログイン中の応答は取り置かせない
        $middleware->append(SecurityHeaders::class);
        // ログインが必要な画面に、ログインしていない人が来たときの行き先（トップ）。
        // AI（ChatGPT・Claude）の同意の画面から来た人だけは、トップのボタンを1回減らすため Google のログインへ直接送る（ログイン後にここへ戻る）
        $middleware->redirectGuestsTo(fn (Request $request) => $request->is('oauth/authorize') ? route('auth.google') : route('home'));
        // ログイン前だけの画面（Google へ送り出すなど）に、ログイン済みの人が来たときの行き先（最初の画面）
        $middleware->redirectUsersTo(fn () => Landing::url());
        // …（省略）…
        $middleware->trustProxies(at: '*');
    })
    ここで決めていること
    • web:：画面の住所の表は routes/web.php。commands: の routes/console.php は、決まった時刻の仕事の表（9章）。
    • alias：自分で作った見張り役 EnsureAgreed に agreed という短い名前を付ける（住所の表で 'agreed' と書けるようにする）。
    • append(SecurityHeaders::class)：どのお願いにも通る見張り役の最後に、守りの札を付ける係を足す（11章）。
    • redirectGuestsTo：ログインが要る住所に、ログインしていない人が来たら、トップ（route('home') ＝ /）へ。ただし ChatGPT・Claude とつなぐときの同意の画面（/oauth/authorize）から来た人だけは、Google のログイン（route('auth.google')）へ直接送ります（13章）。
    • redirectUsersTo：ログイン前だけの住所（Google へ送り出すなど）に、ログイン済みの人が来たら、最初の画面（Landing::url() ＝ /today）へ。
    • trustProxies：本番では CloudFront（https の受付）の後ろで動くので、CloudFront が付ける「本当のアクセス元」の印を信じる（回数制限で使う）。

見張り役（ミドルウェア）

  1. 見張り役

    見張り役は、受付に届く前に順番に確かめる

    ミドルウェア（この解説では「見張り役」）は、お願いが受付（コントローラー）に届く前と、返事が出ていく前に、決まった確認をする係です。何枚も重なっていて、外側から順に通ります。どれか1枚が「ここで止める」と決めると、受付まで届かずに返事（転送やエラー）が返ります。

    たとえるとビルの入口のゲートが何枚も並んでいるようなものです。手荷物検査・入館証の確認・行き先の階の確認…と順番に通り、全部通った人だけが目当ての部屋（受付）に着きます。帰りも同じゲートを逆向きに通るので、出口で「控え」を渡すゲート（守りの札を付ける係）も作れます。

    推理手帳で通る見張り役は、大きく3段です。名前は Laravel 本体の部品で、src/vendor/laravel/framework にあります。

  2. 見張り役

    1段目：どのお願いも通る（全体）

    src/vendor/laravel/framework/src/Illuminate/Foundation/Configuration/Middleware.php
    public function getGlobalMiddleware()
{
    $middleware = $this->global ?: array_values(array_filter([
        \Illuminate\Http\Middleware\ValidatePathEncoding::class,
        \Illuminate\Foundation\Http\Middleware\InvokeDeferredCallbacks::class,
        $this->trustHosts ? \Illuminate\Http\Middleware\TrustHosts::class : null,
        \Illuminate\Http\Middleware\TrustProxies::class,
        \Illuminate\Http\Middleware\HandleCors::class,
        \Illuminate\Foundation\Http\Middleware\PreventRequestsDuringMaintenance::class,
        \Illuminate\Http\Middleware\ValidatePostSize::class,
        \Illuminate\Foundation\Http\Middleware\TrimStrings::class,
        \Illuminate\Foundation\Http\Middleware\ConvertEmptyStringsToNull::class,
    ]));
    主なもの
    • TrustProxies：CloudFront の後ろでも、元は https だったことや、本当のアクセス元を読み取る。
    • PreventRequestsDuringMaintenance：メンテナンス中なら、ここで止めて知らせの画面を返す。
    • ValidatePostSize：送られてきた中身が大きすぎないか。
    • TrimStrings・ConvertEmptyStringsToNull：入力の前後の空白を取り、空の欄を「値なし」（null）にする。
    • 最後に bootstrap/app.php で足した SecurityHeaders。手元で Laravel に並びを出させると、ValidatePathEncoding → InvokeDeferredCallbacks → TrustProxies → HandleCors → PreventRequestsDuringMaintenance → ValidatePostSize → TrimStrings → ConvertEmptyStringsToNull → SecurityHeaders の順でした。
  3. 見張り役

    2段目：画面の住所はどれも通る（web のひとまとまり）

    routes/web.php から読み込んだ住所には、Laravel が web という名前のひとまとまりの見張り役を自動で付けます。

    src/vendor/laravel/framework/src/Illuminate/Foundation/Configuration/Middleware.php
    'web' => array_values(array_filter([
    \Illuminate\Cookie\Middleware\EncryptCookies::class,
    \Illuminate\Cookie\Middleware\AddQueuedCookiesToResponse::class,
    \Illuminate\Session\Middleware\StartSession::class,
    \Illuminate\View\Middleware\ShareErrorsFromSession::class,
    \Illuminate\Foundation\Http\Middleware\PreventRequestForgery::class,
    \Illuminate\Routing\Middleware\SubstituteBindings::class,
    $this->authenticatedSessions ? 'auth.session' : null,
])),
    それぞれの役目
    • EncryptCookies：Cookie を暗号にしたり、元に戻したりする。
    • AddQueuedCookiesToResponse：プログラムの途中で「渡したい」と決めた Cookie を返事に付ける。
    • StartSession：番号札（セッションの Cookie）から、その人の預かり箱（セッション）を開く。ログインしている人の見分けもここから始まる（1章）。
    • ShareErrorsFromSession：前の入力の誤り（「題名を入れてください」など）を画面で使えるようにする。
    • PreventRequestForgery：ほかのサイトから勝手に送られた POST でないかを、合言葉で確かめる（CSRF の対策。11章）。
    • SubstituteBindings：住所の中の {case} や {task} を、データベースの行に取り換える（この章の後半）。
  4. 見張り役

    3段目：住所ごとに付けたもの（auth・agreed・guest・throttle・can）

    住所の表で、住所ごとに付ける見張り役です。短い名前（エイリアス）で書きます。Laravel が最初から持っている名前の表から、推理手帳で使うものを抜き出します。

    src/vendor/laravel/framework/src/Illuminate/Foundation/Configuration/Middleware.php
    'auth' => \Illuminate\Auth\Middleware\Authenticate::class,
// …（省略）…
'can' => \Illuminate\Auth\Middleware\Authorize::class,
'guest' => \Illuminate\Auth\Middleware\RedirectIfAuthenticated::class,
    推理手帳で使う住所ごとの見張り役
    • auth（Authenticate）：ログインした人だけ通す。ログインしていなければトップ / へ（1章）。
    • agreed（EnsureAgreed。推理手帳が作ったもの）：利用規約・プライバシーポリシー・年齢の確認に同意した人だけ通す。まだなら /agree へ（1章）。
    • guest（RedirectIfAuthenticated）：ログインしていない人だけ通す。ログイン済みなら /today へ（1章）。
    • throttle:名前（ThrottleRequests）：1分あたりの回数を数え、多すぎたら 429 で止める。名前（auth・writes・account・calendar）ごとに上限が違う（11章）。
    • can:動作,穴の名前（Authorize）：その記録をこの人が見てよいか・直してよいかを、Policy（権限の係）に聞く。だめなら 403（この章の後半と 11章）。
  5. 見張り役

    見張り役は「決まった優先順位」に並べ替えてから動く

    2段目と3段目は、書いた順のままではなく、Laravel の優先順位の表で並べ替えてから動きます。

    src/vendor/laravel/framework/src/Illuminate/Foundation/Http/Kernel.php
    protected $middlewarePriority = [
    \Illuminate\Foundation\Http\Middleware\HandlePrecognitiveRequests::class,
    \Illuminate\Cookie\Middleware\EncryptCookies::class,
    \Illuminate\Cookie\Middleware\AddQueuedCookiesToResponse::class,
    \Illuminate\Session\Middleware\StartSession::class,
    \Illuminate\View\Middleware\ShareErrorsFromSession::class,
    \Illuminate\Contracts\Auth\Middleware\AuthenticatesRequests::class,
    \Illuminate\Routing\Middleware\ThrottleRequests::class,
    \Illuminate\Routing\Middleware\ThrottleRequestsWithRedis::class,
    \Illuminate\Contracts\Session\Middleware\AuthenticatesSessions::class,
    \Illuminate\Routing\Middleware\SubstituteBindings::class,
    \Illuminate\Auth\Middleware\Authorize::class,
];

    表にある見張り役だけがこの順に入れ替わり、表にない見張り役（推理手帳の agreed）は書いた位置に残ります。たとえば「タスクを済ませる」（POST /tasks/{task}/done。3章）の住所について、手元で Laravel に並びを出させると、次の順でした。

    1. EncryptCookies → AddQueuedCookiesToResponse → StartSession → ShareErrorsFromSession → PreventRequestForgery（ここまで web のひとまとまり）
    2. Authenticate（auth）：ログインしているか
    3. ThrottleRequests:writes：回数が多すぎないか
    4. SubstituteBindings：住所の {task} をタスクの行に替える
    5. EnsureAgreed（agreed）：同意したか
    6. Authorize:update,task（can）：そのタスクの持ち主か
    ここが大事StartSession が auth より前なのは、セッションを開かないと「ログインしているか」が分からないからです。can（Authorize）がいちばん最後なのは、住所の番号を行に替えたあとでないと「この行の持ち主か」を確かめられないからです。回数を数える throttle は行を探すより前なので、ない番号への頼み（404 になるもの）も1回と数えます。

住所の表（routes）の読み方

  1. サーバー

    routes/web.php は、機能ごとのファイルを読み込むだけ

    src/routes/web.php
    // routes/web/ の .php を名前の順に1つずつ読み込む（新しい機能はファイルを置けば読み込まれる）
foreach (glob(__DIR__.'/web/*.php') as $file) {
    require $file;
}

    glob は「この形に合うファイルの名前を集める」関数で、名前の順に並べて返します。require は、そのファイルの中身をここに書いたのと同じように読み込みます。なので、住所の中身は routes/web/ の10のファイル（ai.php・auth.php・calendar.php・cases.php・guide.php・legal.php・review.php・settings.php・tasks.php・today.php）にあります。1つのファイルが長くなりすぎないよう（住所のファイルは120行まで）、機能ごとに分けています。

    たとえるとビルの総合案内板です。web.php は「1階は○○、2階は△△」という階ごとの案内板を貼り合わせているだけで、各階の部屋の案内（どの住所がどの受付か）は階ごとの案内板（web/{機能}.php）に書いてあります。
  2. サーバー

    1行の読み方と、囲み（グループ）

    src/routes/web/today.php
    Route::middleware(['auth', 'agreed'])->group(function () {
    Route::get('/today', TodayController::class)->name('today');
});
    読み方
    • Route::get：GET で来たとき（Route::post なら POST、patch・put・delete も同じ）。
    • '/today'：住所。
    • TodayController::class：受付 src/app/Http/Controllers/Today/TodayController.php。関数の名前を書かないときは、その受付の __invoke()（1つの仕事だけをする受付の決まった名前）を呼ぶ。2つ以上の仕事を持つ受付は [CaseController::class, 'show'] のように関数の名前も書く。
    • ->name('today')：この住所の ルート名。プログラムの中では住所を直接書かず、route('today') と名前で書く（住所を変えても1か所で済む）。
    • Route::middleware([...])->group(function () { … })：囲みの中の住所は、全部その見張り役を通る。推理手帳では、ログインが要る住所はみな ['auth', 'agreed'] の囲みの中にあります。
  3. サーバー

    書き込みの住所には回数制限と権限を付ける

    記録を書く住所は、さらに throttle:writes の囲みに入れ、住所の中に記録の番号があるときは ->can() で持ち主かを確かめます。

    src/routes/web/cases.php
    Route::middleware(['auth', 'agreed'])->group(function () {
// …（省略）…
    Route::get('/cases/{case}', [CaseController::class, 'show'])->can('view', 'case')->name('cases.show');

    Route::middleware('throttle:writes')->group(function () {
        Route::post('/cases', [CaseController::class, 'store'])->name('cases.store');
// …（省略）…
        // 手がかり（閉じた事件には足せない・直せない・消せない）
        Route::post('/cases/{case}/clues', [ClueController::class, 'store'])->can('write', 'case')->name('clues.store');
    • {case} は住所の穴（ルートパラメータ）。/cases/12 が来ると、穴 case に 12 が入ります。
    • ->can('view', 'case') は、見張り役 can:view,case を付けるのと同じです（Laravel 本体の Route::can が $this->middleware(['can:'.$ability.','.implode(',', Arr::wrap($models))]) を呼ぶ）。「穴 case の記録を view（見る）してよいか」を Policy に聞きます。
    • ->can('write', 'case') は推理手帳が足した能力で、「持ち主で、事件が捜査中か」を聞きます。閉じた事件に手がかりや見立てを書き込ませないためです（11章）。

    決まった形の「一覧・作る・直す・消す」は、Route::resource で1行にまとめます。屋根裏の棚の住所はこう書いてあります。

    src/routes/web/review.php
    Route::resource('attic', AtticNoteController::class)
    ->only(['index', 'store', 'update', 'destroy'])
    ->parameters(['attic' => 'note'])
    ->middlewareFor('store', 'throttle:writes')
    ->middlewareFor('update', ['throttle:writes', 'can:update,note'])
    ->middlewareFor('destroy', ['throttle:writes', 'can:delete,note']);

    これで GET /attic（index）・POST /attic（store）・PUT|PATCH /attic/{note}（update）・DELETE /attic/{note}（destroy）の4つの住所ができます。parameters で穴の名前を {note} にし、middlewareFor で動作ごとに見張り役を付けています。

  4. 見張り役

    穴の番号を記録の行に替える（SubstituteBindings）

    穴 case の中身は、まだ 12 という文字です。受付が欲しいのは事件の表の1行なので、受付に渡す前に、見張り役 SubstituteBindings が番号を行に替えます。この働きをルートモデルバインディング（住所とモデルを結びつけること）と呼びます。

    ふつうは、受付の関数の引数の型と名前から自動で決まります（Task $task なら穴 task の番号で tasks 表を探す）。事件だけは、名前の付け方の都合で、どの表かを自分で教えています。

    src/app/Providers/AppServiceProvider.php
    // 住所の {case} は「事件」（CaseFile）。case は PHP の予約語なのでモデルの名前と住所の名前がちがう
Route::model('case', CaseFile::class);

    case は PHP の予約語（switch の中で使う言葉）なので、事件のモデルは CaseFile、表は case_files という名前です。住所の穴は読みやすく {case} のままにし、「穴 case は CaseFile で探す」と結びつけています。見張り役はこの結びつきを見て、穴の中身を行に入れ替えます。

    src/vendor/laravel/framework/src/Illuminate/Routing/Router.php
    public function substituteBindings($route)
{
    foreach ($route->parameters() as $key => $value) {
        if (isset($this->binders[$key])) {
            $route->setParameter($key, $this->performBinding($key, $value, $route));
        }
    }

    return $route;
}

    その番号の行がなければ「見つからない」として 404 の画面になります。他人の事件の番号なら、行は見つかりますが、次の can で止まります（403）。

    このとき動くデータ
    • 読む：case_files の1行（id = 12）
  5. 見張り役

    can：持ち主かを Policy に聞く

    can:view,case の見張り役（Authorize）は、穴 case に入った行（CaseFile）を持って、その種類の Policy（App\Policies\CaseFilePolicy。モデルの名前＋Policy という名前の決まりで Laravel が自動で見つける）の view を呼びます。推理手帳の Policy はどれも同じ部品 OwnerOnly を使っています。

    src/app/Policies/Concerns/OwnerOnly.php
    /** 記録の持ち主がこの人かを返す（型をそろえて比べる） */
protected function owns(User $user, Model $record): bool
{
    return (int) $record->getAttribute('user_id') === (int) $user->getKey();
}

    記録の user_id（持ち主の番号）とログイン中の人の番号が同じときだけ許し、違えば 403 で止めます。くわしくは 11章。

    たとえると貸し金庫の窓口です。番号札で金庫を出してくる（SubstituteBindings）のと、その金庫の名義が本人か確かめる（can）のは別の係で、名義が違えば開けずに断ります。

受付から画面まで：層の分担

  1. サーバー

    受付は薄く、仕事は係に分ける（太らない MVC）

    見張り役を全部通ると、住所の表で決めた受付の関数が呼ばれます。推理手帳では、1つのファイルに1つの役目だけを持たせ、受付（コントローラー）を薄く保っています。役目の分け方と行数の上限は .claude/rules/architecture.md にあり、bin/check が機械でも確かめます。

    層と置き場所
    • 受付（Controller）src/app/Http/Controllers/{機能}/：受け取る → 係を呼ぶ → 画面か転送を返す。1つの動作は10行くらいが目安。決まりそのものは持たない。
    • 形の検証（FormRequest）src/app/Http/Requests/{機能}/：送られてきた値の形を確かめる（必須か・何文字までか・選べる値か）。だめなら受付まで届かずに元の画面へ戻す（入力とエラーを持って）。
    • 権限（Policy）src/app/Policies/：この人がこの記録を見てよいか・直してよいか（持ち主か）。
    • 用事（Action）src/app/Actions/{機能}/：1つの用事（手がかりを足す・答え合わせをする）を1つのクラスで。呼び出し口は handle() だけ。いくつもの表に書くときは、全部書くか全部書かないかのまとまり（トランザクション）にする。
    • 読み出しのまとめ（Query）src/app/Queries/{機能}/：画面に出す一覧や集計を組み立てる。書き込みはしない。
    • 外とのやりとり（Service）src/app/Services/{相手}/：Google カレンダーなど。テストのときに偽物に差し替えられるよう、窓口の型（src/app/Contracts/）越しに使う。ワトソンのひとことや週の集計のような「決まった規則の計算」もここ。
    • 表（Model）src/app/Models/：データベースの1つの表を、プログラムから扱う形にしたもの（CaseFile は case_files 表、Task は tasks 表）。
    • 列挙（Enum）src/app/Enums/：状態や種類（手がかりの「見た・聞いた・なかった」など）。画面の言葉は config/suiri.php から引く。
    • 後回しの仕事（Job）src/app/Jobs/：Google への書き出し・取り込み。worker の箱が片づける。
    • 画面（Blade）と部品src/resources/views/{機能}/ と src/resources/views/components/{分類}/：HTML の型紙。画面は部品（<x-case-step.clue-card> など）を並べるだけ。
    • 設定値と文言src/config/suiri.php（ワトソンは watson.php、決まりごとのページは legal.php、ChatGPT・Claude とつなぐ窓口は ai_connect.php）：数字・文言・選択肢。コードに直書きしない。
    たとえると役所の窓口です。窓口の人（受付）は書類を受け取り、記入漏れの確認係（FormRequest）・本人確認係（Policy）・担当課（Action）・資料室（Query）に回し、できあがった書類を決まった様式（Blade）に書いて渡します。窓口の人自身は、決まりを覚えていなくてもよいのです。
  2. サーバー

    薄い受付の例：手がかりを足す

    src/app/Http/Controllers/Cases/ClueController.php
    /** 手がかりを足して、事件の詳細の手がかりのところへ戻す */
public function store(StoreClueRequest $request, CaseFile $case, AddClue $addClue): RedirectResponse
{
    $clue = $addClue->handle($case, $request->validated('kind'), $request->validated('body'));

    return $this->backToCase($case, '手がかりを足しました。', [$clue->body], 'clues');
}

    引数は Laravel が用意します。

    • StoreClueRequest $request：形の検証の係。引数にあるだけで、関数が動く前に検証が済みます。通った値だけを validated('kind') で取り出します。
    • CaseFile $case：見張り役 SubstituteBindings が穴 {case} を替えておいた事件の行。持ち主かは can で確かめ済み。
    • AddClue $addClue：手がかりを足す用事。Laravel がその場で作って渡します（依存性の注入：必要な道具を自分で作らず、外から渡してもらうしくみ）。

    受付がしているのは「用事を呼んで、事件の画面へ転送する」だけです。続きは 5章 で追います。

  3. サーバー

    画面の言葉は config から引く（列挙と label()）

    手がかりの種類のような「決まった選択肢」は列挙（Enum）で表し、データベースには英語の値（seen）を入れ、画面の言葉（「見た」）は config/suiri.php から引きます。仕事の場面では言い方を変えられるよう、言葉をコードに直書きしません。

  4. ブラウザ

    画面の骨組みと、JavaScript は「使いやすくする」ためだけに足すこと

    ログインしたあとの画面は、どれも同じ骨組み（レイアウト）<x-layouts.app> の中に中身をはめこんで作ります。上に画面の名前と設定のアイコンの帯、スマホでは下に固定のナビ（今日・タスク・事件・手引き・ふりかえり）、パソコンでは左に縦のナビが付きます。

    src/resources/views/components/layouts/app.blade.php
    <meta name="csrf-token" content="{{ csrf_token() }}">
<title>{{ $title }}｜{{ config('app.name') }}</title>
{{-- …（省略）… --}}
@vite(['resources/css/app.css', 'resources/js/app.js'])
{{-- …（省略）… --}}
<main class="mx-auto {{ $width }} px-4 pt-4 pb-32 md:pt-6 md:pb-12">
  <x-ui.flash />
  {{ $slot }}
  <x-layouts.footer class="mt-12" />
</main>
    • {{ … }} は「値を画面にはめこむ」書き方です。中の文字は、HTML の記号として働かないように自動で置き換えられます（< は &lt; に）。利用者が書いた文に <script> と書いてあっても、プログラムとしては動きません。
    • @vite は、ビルドした CSS と JavaScript のファイルを読み込む行を作ります。
    • <x-ui.flash /> は、転送のときに渡したお知らせ（「手がかりを足しました。」など）を出す部品です。
    • {{ $slot }} の所に、画面ごとの中身が入ります。
    • {{ $width }} は中身の幅です。ふだんは max-w-3xl（スマホで読みやすい幅）で、左右2列に分ける事件の画面だけ、パソコンで広げます（<x-layouts.app title="…" wide>）。
    src/resources/js/app.js
    /*
  画面の動きの入口。ここは読み込むだけにして、動きは resources/js/parts/{部品}.js に1部品1ファイルで書く。
  土台の部品（消す前の確認など）は JavaScript なしで動く（<details> を使う）。
*/
import './parts/suggest-chips.js';
import './parts/minute-chips.js';
import './parts/stepper.js';
import './parts/ai-copy.js';

    app.js は4つの部品の動きを読み込むだけです。どれも「使いやすくするために足した動き」で、保存はしません。

    • suggest-chips.js：提案のチップ（手がかりの問いかけ・別の説明の型・予想の穴埋め・確かめる日の候補）を押すと、入力欄に書き出しが入るだけ。送るのは本人です（5章・6章）。
    • minute-chips.js：「何分かかりそう？」のよく使う分のボタンを押すと、分の欄に数が入る（3章）。
    • stepper.js：事件を作る画面で、1つのフォームの段を1問ずつ見せ、「つぎへ」で進める。送るのは最後の1回だけ（4章）。
    • ai-copy.js：写すボタンを押すと、欄の文を端末のクリップボードに写す。アプリからはどこにも送らない（13章）。

    どの動きも、JavaScript が動かないときはボタンが隠れたままで、ふつうのフォームとして書いて送れます。推理手帳の画面の土台は、ふつうのフォームとリンクです。ボタンを押すとフォームが送られ、サーバーが記録を書いて転送し、ブラウザが新しい画面を開き直す、という1往復の繰り返しです。「消す前の確認」も、開け閉めできる HTML の部品 <details> で作っています。

    src/resources/views/components/ui/confirm.blade.php
    <details {{ $attributes->class(['group']) }}>
{{-- …（省略）… --}}
    <form method="POST" action="{{ $action }}" class="mt-3">
      @csrf
      @method($method)
      {{ $slot }}
      <x-ui.button variant="danger">{{ $confirmLabel }}</x-ui.button>
    </form>
  </div>
</details>

    @csrf は合言葉の隠し欄 _token を、@method($method) は隠し欄 _method（たとえば DELETE）を、フォームの中に作ります。

    ここが大事どの章でも、ブラウザの段は「フォームを送る」か「リンクを開く」です。サーバーの返事が転送（302）なら、ブラウザはすぐに転送先へ GET を送り直し、その返事の HTML を表示します。1章 からは、この往復を1歩ずつ追います。
  5. サーバー

    画面を待たせない仕事は worker の箱へ

    Google カレンダーへの書き出しのように、外のサービスを待つ仕事は、お願いの途中ではしません。「この仕事をあとでして」という札（Job）を jobs 表に積むだけにして、すぐに返事を返し、worker の箱の queue:work があとで片づけます。決まった時刻の仕事は routes/console.php に書いてあります。

    src/routes/console.php
    Schedule::job(new PullCalendarChanges)->cron('*/'.config('suiri.calendar.pull_every_minutes').' * * * *');

// 期限の過ぎたキャッシュの行を5分ごとに消す（今日の予定の題名と時刻を、覚えておく5分を過ぎて表に残さないため）
Schedule::command('cache:prune-expired')->everyFiveMinutes();

    タスクを保存すると書き出しの仕事が積まれるところは 3章、その仕事の中身と15分ごとの取り込みは 9章、今日の予定を5分だけ覚えておくところは 2章 で追います。

    たとえるとクリーニング店の受付です。服を預かったら引換券を渡してすぐに帰ってもらい（返事）、洗うのは奥の工場（worker）があとでします。客は洗い上がるまで店で待たなくてよいのです。
この章のまとめ
  1. どの行動も「お願い（リクエスト）」と「返事（レスポンス）」の1往復。推理手帳の返事は、ほとんどが HTML か転送。
  2. サーバーは web・app・db・worker の4つの箱。web がファイルならそのまま返し、ほかは public/index.php から Laravel へ。
  3. 見張り役は「全体 → web のひとまとまり → 住所ごと（auth・agreed・guest・throttle・can）」。Laravel の優先順位の表で並べ替えてから動き、can は住所の番号を行に替えたあとに動く。
  4. routes/web.php は routes/web/{機能}.php を読み込むだけ。ログインが要る住所は ['auth', 'agreed'] の囲み、書き込みは throttle:writes、記録の番号がある住所は ->can()。AI の会社のサーバーが呼ぶ住所だけは別の routes/ai.php で、web のひとまとまりの外（13章）。
  5. 受付は薄く、形の検証（FormRequest）・権限（Policy）・用事（Action）・読み出し（Query）・外とのやりとり（Service）・画面の部品に分ける。外を待つ仕事は Job にして worker の箱へ。
