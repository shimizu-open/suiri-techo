6もしそうなら：予想を立てる

見立てを立てた人として、その見立てが本当かどうかを、あとで確かめられる形にしておきたい。だから、事件の画面の「もしそうなら、何が見える？」のカードで、1問ずつ「〜が見えるはず」・どのくらい自信があるか・いつ確かめるかに答えて保存する。

この章で追う道筋：「もしそうなら、何が見える？」のカード（case-step/predict-card。1問ずつ・穴埋めの型と確かめる日の候補のチップ）→ POST /hypotheses/{hypothesis}/predictions → 見張り役（web のひとまとまり → auth → throttle:writes → SubstituteBindings → agreed → can:write,hypothesis）→ 形の検証 StorePredictionRequest → 受付 PredictionController::store → 用事 MakePrediction（predictions 表に1行 ＋ 確かめるタスクを tasks 表に1行）→ 見張り係 TaskObserver がカレンダーへの書き出しを予約 → 事件の画面へ転送 → 「〇月〇日に確かめよう」のカード。後半で「予想の文と確かさが書き換えられない仕組み」と「取り下げ」（POST /predictions/{prediction}/withdraw）も追います。

  8. 見張り役

    見張り役が並ぶ順番

    Laravel は見張り役を決まった優先順位に並べ替えてから動かします（0章）。この住所で実際に動く順を Laravel に出させると、次のとおりでした。

    1. EncryptCookies・AddQueuedCookiesToResponse・StartSession・ShareErrorsFromSession：クッキーとセッションの準備（1章）
    2. PreventRequestForgery：合言葉 _token を確かめる（11章）
    3. Authenticate（auth）：ログインしているか（1章）
    4. ThrottleRequests:writes：書きこみが1分に60回を超えていないか（11章）
    5. SubstituteBindings：穴の 12 を見立ての行に取り換える
    6. EnsureAgreed（agreed）：利用規約などに同意しているか（1章）
    7. Authorize:write,hypothesis（can）：この見立ての持ち主で、事件が捜査中か
    ここが大事持ち主かどうかの確かめ（Authorize）は、いちばん最後です。持ち主を確かめるには見立ての行が要るので、穴を行に取り換える SubstituteBindings より後でなければなりません。
  9. 見張り役

    SubstituteBindings：穴の 12 を見立ての行に替える

    受付の関数は store(StorePredictionRequest $request, Hypothesis $hypothesis, …) のように、引数で Hypothesis（見立ての表 hypotheses の1行を表すモデル）を欲しがっています。SubstituteBindings は、穴の名前 hypothesis と引数の名前 $hypothesis が同じなのを見て、hypotheses 表から id = 12 の行を読み、穴の中身をその行に入れ替えます。この働きをルートモデルバインディング（住所とモデルを結びつけること）と呼びます。

    • そんな番号の見立てがなければ、ここで「404（見つからない）」になり、受付まで届きません。
    このとき動くデータ
    • 読む：hypotheses の1行（id = 12）
  10. 見張り役

    can:write,hypothesis：この見立ての持ち主で、事件が捜査中か（Policy）

    ルートの ->can('write', 'hypothesis') は、Laravel の中で「can:write,hypothesis という見張り役を足す」に置き換わります。

    src/vendor/laravel/framework/src/Illuminate/Routing/Route.php
    public function can($ability, $models = [])
{
    $ability = enum_value($ability);

    return empty($models)
        ? $this->middleware(['can:'.$ability])
        : $this->middleware(['can:'.$ability.','.implode(',', Arr::wrap($models))]);
}

    その見張り役 Authorize は、穴 hypothesis の中身（もう見立ての行になっている）を取り出し、門番（Gate）に「この人は、この見立てに write（書き込む）してよいか」と聞きます。

    src/vendor/laravel/framework/src/Illuminate/Auth/Middleware/Authorize.php
    public function handle($request, Closure $next, $ability, ...$models)
{
    $this->gate->authorize($ability, $this->getGateArguments($request, $models));

    return $next($request);
}

    門番は、モデルの名前から決まりの係 Policy（だれが何をしてよいかを決める係）を見つけます。Hypothesis なら HypothesisPolicy です。中身は「持ち主だけ」の共通部品 OwnerOnly と、「捜査中の事件にだけ書き込める」の共通部品 WritesOpenCase を使うだけです。

    src/app/Policies/HypothesisPolicy.php
    class HypothesisPolicy
{
    use OwnerOnly, WritesOpenCase;
}
    src/app/Policies/Concerns/WritesOpenCase.php
    public function write(User $user, Model $record): Response
{
    // 持ち主でなければ断る（他人の記録は、閉じているかどうかを知らせずに 403）
    if (! $this->owns($user, $record)) {
        return Response::deny();
    }

    $case = $record instanceof CaseFile ? $record : $record->getAttribute('caseFile');

    // 事件が捜査中なら通し、閉じていれば開き直すよう伝えて断る
    return $case->isOpen() ? Response::allow() : Response::deny(config('suiri.cases.closed_message'));
}
    src/app/Policies/Concerns/OwnerOnly.php
    /** 記録の持ち主がこの人かを返す（型をそろえて比べる） */
protected function owns(User $user, Model $record): bool
{
    return (int) $record->getAttribute('user_id') === (int) $user->getKey();
}

    まず見立ての行の user_id と、ログイン中の人の id が同じかを owns で見ます。違えば「403（してはいけない）」です。次に、見立ての事件（caseFile）が捜査中かを見て、閉じた（解決・迷宮入り）事件なら「事件を開き直してください」の文つきで 403 にします。予想を立てるのは「その見立てに書き足すこと」なので、見立ての write の権利で確かめています。

    たとえるとロッカーに物を入れる前に、係の人が「このロッカーの鍵の名札が、あなたの名前と同じか」を見るようなものです。番号を書き換えて他人のロッカーを指しても、名札が違うので開けられません。

    3. rules() の決まりで中身を確かめる。合わなければ failedValidation で、入力の間違いを持って元の画面へ戻す。

    StorePredictionRequest の中身：見せ合ったあとか・文・確かさ・確かめる日

    src/app/Http/Requests/Cases/StorePredictionRequest.php

public function authorize(): bool
{

/** 送る前に、文の前後の空白を取る */
protected function prepareForValidation(): void

/**
 * 項目ごとの決まり（確かさの選択肢は config/suiri.php の confidence.choices）。
 * 文に穴埋めの印（＿＿。予想の穴埋めの提案 S-3 が入れる）が残っていたら通さない（保存後は直せないため、書き換えてから保存してもらう）
 */
public function rules(): array
{
    return [
        'statement' => ['required', 'string', 'max:'.config('suiri.limits.prediction_statement'), 'not_regex:/'.preg_quote(config('suiri.suggest.blank'), '/').'/u'],
        'confidence' => ['required', 'integer', Rule::in(array_keys(config('suiri.confidence.choices')))],
        'check_on' => ['required', 'date_format:Y-m-d', 'after_or_equal:today'],
        'check_at' => ['nullable', 'date_format:H:i'],
        'attic_note_id' => ['nullable', 'integer', Rule::exists('attic_notes', 'id')->where('user_id', $this->user()->id)],
    ];
}
    • authorize：見立ての事件（caseFile）が相棒モードの見せ合う前でないときだけ通します（見せ合う前なら 403）。持ち主か・事件が捜査中かは、もう前の見張り役（write）で確かめ済みです。画面では閉じた事件に予想のカードを出しませんが、住所を直接打って送られることもあるので、見張り役がサーバーでも止めます。
    • statement（予想の文）：必ず要る。前後の空白を取ったうえで300字まで（config/suiri.php の limits.prediction_statement。表の列の長さと同じ）。さらに not_regex（この形を含んでいたら通さない）で、穴埋めの印 ＿＿ が残った文を断ります。「型を使う」で入れた型を書き換えずに保存すると、あとで直せないまま「＿＿」の予想が残ってしまうからです。
    • confidence（確かさ）：Rule::in で、設定の選択肢の数（50・55・…・95）のどれかだけを受け付けます。72 や 100 は通りません。
    • check_on（確かめる日）：2026-10-31 の形で、今日以降（after_or_equal:today）。アプリの時計は日本時間（config/app.php の timezone が Asia/Tokyo）なので、「今日」は日本の今日です。
    • check_at（確かめる時刻）：なくてもよい。あれば 07:40 の形。
    • attic_note_id（使う屋根裏の知識）：なくてもよい。あれば attic_notes 表に「その番号で、しかも user_id がこの人」の行があるときだけ通します。他人の棚の知識の番号を送っても使えません。

    • answeredByPrediction：予想から作った確かめるタスクで、もとの予想が残っているか。
    • checksPendingPrediction：そのうえで、予想がまだ答え合わせ待ちか。

    タスクを直す送信の係は、確かめるタスクなら題名の決まりを外します。決まりにない項目は validated() に入らないので、題名（予想の文の写し）を送られても受け取りません。

    unset($rules['title']);
}
// 答え合わせ待ちの予想を確かめるタスクなら、期日を必須にする（予想の確かめる日を空にしない）
if ($task->checksPendingPrediction()) {
    $rules['due_on'] = ['required', 'date_format:Y-m-d'];
}

  25. サーバー

    用事 WithdrawPrediction：取り下げた日時を入れ、確かめるタスクを消す

    src/app/Actions/Cases/WithdrawPrediction.php
    public function handle(Prediction $prediction): bool
{
    return DB::transaction(function () use ($prediction) {
        // 保存されている今の状態を、ほかの書き込みを待たせて読み直す（同時の答え合わせと食い違わないように）
        $current = Prediction::whereKey($prediction->getKey())->lockForUpdate()->first();

        // もう答え合わせ済み・取り下げ済み（または消えた）なら、何もしない
        if ($current === null || ! $current->isPending()) {
            return false;
        }

        $prediction->update(['withdrawn_at' => now()]);

        $task = $prediction->task;
        // 確かめるタスクがまだ済んでいなければ消す（済んだものは記録として残す）
        if ($task !== null && ! $task->isDone()) {
            $task->delete();
        }

        return true;
    });
}
    • lockForUpdate()：この予想の行に鍵（行のロック）をかけて読み直します。トランザクションが終わるまで、ほかの書きこみはこの行を待たされます。別の画面で同時に答え合わせが送られても、どちらか先の1つだけが通ります。
    • 受付の検証でも確かめていますが、ここでもう一度 isPending() を確かめます（最後の守り）。
    • update(['withdrawn_at' => now()])：取り下げた日時だけを入れます。文と確かさは残るので、手順21の updating の見張りも通ります。
    • まだ済んでいない確かめるタスクは delete() で消します。すると TaskObserver の deleted が動き、カレンダーの予定を消す仕事 RemoveTaskFromCalendar を（確定のあとに）積みます（9章）。
    このとき動くデータ
    • 読む（鍵をかけて）・書く：predictions のこの行（withdrawn_at）
    • 消す：tasks の確かめるタスクの行（済んでいなければ）

    受付 WithdrawPredictionController は、終わったら「予想を取り下げました。確かめるタスクも消しました。」のお知らせを付けて、backToCase で事件の画面へ戻します（場所の印 #hyp-…）。進み具合の「もしそうなら」には「取り下げた：（予想の文）」と残り、答え合わせ待ちの予想がなくなったので、いまの一手はまた「予想を立てる」に戻ります。

この章のまとめ
  1. 予想を立てるカードは、いまの一手が predict のときか、?open=predict-{id} で頼まれたときに出る。対象は捜査中の事件の、見せ合う前でない・消えていない見立てだけ。
  2. カードは1問ずつ（見えるはずのこと → 自信 → 確かめる日）。次の問いは CSS の :has で、前の問いに答えるまで隠す。穴埋めの型と確かめる日の候補（すぐ選べる日・言葉の重なる自分の予定）は、押すと欄に入るだけ。
  3. POST /hypotheses/{hypothesis}/predictions は、ログイン・同意・回数制限・持ち主で捜査中か（HypothesisPolicy::write）を通ってから、StorePredictionRequest が見せ合ったあとか・文（穴埋めの印が残っていないか）・確かさ（50〜95 の5刻み）・確かめる日（今日以降）・自分の棚の知識だけかを確かめる。
  4. MakePrediction が、1つのトランザクションで「予想の行」と「確かめるタスク（kind=verify）」を作る。TaskObserver が、つないでいる人なら確定のあとにカレンダーへの書き出しの仕事を積む（9章）。
  5. 保存のあとは「〇月〇日に確かめよう」のカードになる。文と確かさは、直す住所がない・モデルの updating が止める・タスクの側からも題名を受け取らず確かめる日だけを写す、の何重もの守りで書き換えられない。
  6. 考えが変わったら取り下げる。答え合わせ待ちの予想だけ、行に鍵をかけて取り下げ、済んでいない確かめるタスクを消す。
